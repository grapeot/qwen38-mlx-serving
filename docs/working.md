## 2. 真实技术陷阱与教训

- `--prefix-cache-mem 0GB` 表示无预算上限，禁用缓存应使用 `--prefix-cache-entries 0`。早期探索出现 7-token 命中，已从最终冷缓存比较中排除。
- 历史筛选中更深的 MTP 和 GPU ngram 没有持续胜过采用配置；不要凭参数大小判断更快。
- CLI 深度上限 6 与 `MLX_SERVE_MTP_FORCE_DEPTH=3` 的实际固定深度要同时记录。
- 8K 草稿历史不限制主上下文；262K 是主模型输入与输出共享的配置上限，测试只到 128K，完整 262K 尚未实测，Vision 默认禁用。
- 默认无思考对 `19×23+7×8` 错答 503；启用思考后答对 493。不能用速度替代质量判断。
- 原 community ngram 与公开 iQ 仓库的表字节不同。历史组合包不等于 canonical checkpoint，不承诺质量等价。
- 部分客户端 SDK 会注入输出上限；DSH 的 pi-ai 链路曾在请求体中写入 `max_completion_tokens:32768`，即使 profile 未设置上限。DSH 本地 model ID 已更新，服务不设 max token，仍需检查实际请求体，不能只看配置。
- macOS 终止中的进程可能先清空 argv；PID 归属在发送 SIGTERM 前检查，等待只查进程状态。
- macOS 的 `python3` 可能是 3.9。本项目明确要求 Python 3.12+，不要靠系统命令名推断版本。
- HF 传输数分钟未完成权重文件时可换 aria2 分段续传；外部工具仅负责搬运，必须锁定清单 URL 与 Hash 且传输后独立校验 113 文件；测试期不预估耗时或判定成功。
- **长上下文算力波动与耗时指标分析（保留首轮下降排查案例）**：在首轮 captured llmprobe 64K 重放测试中，前两次运行的草稿命中率几乎完全相同（原始记录为 81.4% 与 81.5%），但单轮计算耗时 `round_ms` 从 34.99ms 陡增至 69.21ms，吞吐发生显著下降（56.1 tok/s）。这表明该轮耗时上升不能仅用草稿接受率变化解释；但需要明确，`round_ms` 是原生引擎报告的解码轮耗时，单独这个字段不能定位物理硬件瓶颈，不能草率断定为硬件物理变慢。而在本次 64K 专项复测中，三次 native `round_ms` 分别为 33.80ms、35.37ms 和 34.85ms，单轮耗时相对稳定；第三次 Decode 速率较慢（81.3 tok/s），同时草稿命中率由前两轮的 81.4% / 81.5% 降低至 59.5%。这表明接受率变化可以解释第三次的部分吞吐波动，与首次重放中命中率相同但 `round_ms` 翻倍的现象有所不同；但同样需要注意，单凭 `round_ms` 无法定位物理硬件瓶颈，不能据此认为物理与内容因素已被完全解耦。
- **热管理与传感器同步记录的严谨边界**：在 64K 与 128K 交替复测中，长上下文 Decode 中位数恢复至 97.5 tok/s 与 100.6 tok/s，未观察到更换模型权重后持续一致的 Decode 退化。但测试期间风扇明显升速（128K 最高达 5300+ RPM，64K 亦达 4800+ RPM），GPU 峰值温度达 97.6°C，GPU 频率动态调整（温度与频率均为瞬时采样值）。由于首轮完整重放未记录温度与频率数据，且本轮复测同时改变了服务实例、执行顺序（64K/128K 交替）和等待间隔（45 秒空闲），后续 97.5 / 100.6 tok/s 的复测数据是在重启+交替+45秒空闲特定条件下测得，不能拼成统一优化后曲线，不能证明热降频就是此前下降的根本原因，也不能保证持续满载运行下始终达到 100 tok/s。因此现有数据既不能证实、也不能排除上一轮存在热降频，**绝不宣称热问题已解决**。系统风扇仍由 macOS 默认管理。首轮完整重放的下降数据作为真实记录必须保留。短上下文 Prefill 在首轮重放中仍较历史基线偏低，不承诺所有指标全面更快；完整 262K 上下文、持续无空闲高负载以及广泛任务生成质量均未经过验证。测试中使用已有 `macmon` pipe 记录 GPU 温度/频率/功耗，风扇转速由本机 SMC 只读采样，不在公开仓库提交私有传感器实现或日志。
